# 19 — Rule Version Control and CI/CD

## SIEM Engineer Interview Questions

### Topic 01: Detection-as-Code (DaC) Principles & Git Repository Architecture

1. ডিটেকশন-অ্যাজ-কোড (Detection-as-Code - DaC) কী এবং ম্যানুয়ালি SIEM ওয়েব কনসোলে রুল লেখার বদলে সফটওয়্যার ইঞ্জিনিয়ারিংয়ের মতো Git রিপোজিটরিতে রুল ও ডিকোডার ম্যানেজ করা কেন আধুনিক এন্টারপ্রাইজের মানদণ্ড?
2. একটি এন্টারপ্রাইজ DaC রিপোজিটরির ডিরেক্টরি স্ট্রাকচার (যেমন: `/rules`, `/decoders`, `/tests`, `/mappings`, `/ci-cd`, `/docs`) কীভাবে ডিজাইন করবে?
3. বিভিন্ন প্ল্যাটফর্মের (যেমন: Wazuh XML, Sigma YAML, Splunk Savedsearches conf, Elastic EQL) জন্য মাল্টি-ফরম্যাট রিপোজিটরি কীভাবে সাজাবে?
4. রুলের মেটাডেটা ট্র্যাকিং: প্রতিটি রুল ফাইলে অথর, ইউনিক ইউআইডি (UUID), ভার্সন নম্বর, ক্রিয়েশন ডেট এবং চেঞ্জলগ কীভাবে স্ট্রাকচার্ড কমেন্ট বা YAML হেডারে সংরক্ষণ করবে?
5. DaC বাস্তবায়নের ফলে এসওসি টিমের ডিটেকশন ডেভেলপমেন্ট লাইফসাইকেল (DDLC) এবং টাইম-টু-মার্কেট (Time-to-Detect) কীভাবে দ্রুত ও নির্ভুল হয়?

### Topic 02: Branching Strategies & Peer Review Workflows

6. ডিটেকশন ইঞ্জিনিয়ারিং টিমের জন্য কোন Git ব্রাঞ্চিং স্ট্র্যাটেজি (GitFlow বনাম GitHub Flow / Trunk-Based) সবচেয়ে উপযোগী এবং কেন?
7. প্রোডাকশন ব্রাঞ্চে (`main` বা `production`) সরাসরি পুশ বা কমিট কঠোরভাবে ব্লক করে কীভাবে পুল রিকোয়েস্ট (Pull Request / Merge Request) বাধ্যতামূলক করবে?
8. একজন ইঞ্জিনিয়ার নতুন রুল বা ডিকোডার সাবমিট করলে অন্তত দুজন সিনিয়র পিয়ার রিভিউয়ারের অ্যাপ্রুভাল (`CODEOWNERS` ফাইল পলিসি) কীভাবে এনফোর্স করবে?
9. পিয়ার রিভিউ চেকলিস্ট: একজন কোড রিভিউয়ার একটি ডিটেকশন PR পর্যালোচনা করার সময় কোন কোন টেকনিক্যাল দিক (লজিক্যাল ফ্ল, পারফরম্যান্স ইমপ্যাক্ট, রেজেক্স ব্যাকট্র্যাকিং, ফলস পজিটিভ রিস্ক) যাচাই করবেন?
10. ইমার্জেন্সি হটফিক্স (Emergency Hotfix / 0-Day Rule Deploy): সক্রিয় সাইবার অ্যাটাকের সময় দ্রুততম সময়ে রুল পুশ করার জন্য ইমার্জেন্সি বাইপাস উইন্ডো ও পোস্ট-ইনসিডেন্ট অডিট কীভাবে পরিচালনা করবে?

### Topic 03: Automated Linting & Static Code Analysis

11. সিআই/সিডি পাইপলাইনে কোড পুশ হওয়ার সাথে সাথে স্বয়ংক্রিয় লিন্টিং (Linting: যেমন XML ভ্যালিডেশন, YAML লিন্ট, JSON স্কিমা চেকিং) কীভাবে কনফিগার করবে?
12. স্ট্যাটিক অ্যানালাইসিস (Static Analysis): রুল কোয়েরির মধ্যে কোনো বিপজ্জনক আন-অপ্টিমাইজড সিনট্যাক্স (যেমন: লিডিং ওয়াইল্ডকার্ড `*query*`, আনবাউন্ডেড সার্চ উইন্ডো) থাকলে পাইপলাইনে স্বয়ংক্রিয় ওয়ার্নিং বা এরর দেওয়ার কাস্টম লিন্টার কীভাবে বানাবে?
13. সিক্রেট স্ক্যানিং (Secret Scanning): ডেভেলপাররা অসাবধানতাবশত রুল বা কনফিগারেশনে এপিআই টোকেন, পাসওয়ার্ড বা ইন্টারনাল ক্রেডেনশিয়াল পুশ করলে তা `gitleaks` বা `trufflehog` দিয়ে কীভাবে ব্লক করবে?
14. নেমিং কনভেনশন ও স্টাইল গাইড এনফোর্সমেন্ট: রুলের আইডি রেঞ্জ (যেমন: কাস্টম রুল ১০০০০০-১৯৯৯৯৯), সিভিয়ারিটি লেভেল এবং রুল ডেসক্রিপশন ফরম্যাট অটো-ভ্যালিডেট করার স্ক্রিপ্ট কীভাবে লিখবে?
15. সিআই রানার্স (GitHub Actions / GitLab Runner)-এ লিন্টিং ফেইল করলে পুরো পাইপলাইন ফেইলিওর এবং ডেভেলপার নোটিফিকেশন পাঠানোর প্রসিডিউর কী?

### Topic 04: Automated Unit & Integration Testing in CI

16. প্রতিটি রুলের জন্য টেস্ট লগ ইনপুট (Mock Events) এবং এক্সপেক্টেড অ্যালার্ট আউটপুট দিয়ে স্বয়ংক্রিয় ইউনিট টেস্ট (Automated Unit Testing) সিআই পাইপলাইনে কীভাবে রান করবে?
17. ডকার কন্টেইনারে একটি লাইটওয়েট SIEM ইঞ্জিন (যেমন: হেডলেস Wazuh বা Elastic টেস্ট কন্টেইনার) স্পিন-আপ করে পাইপলাইনের ভেতরেই রিয়েল ডিকোডিং ও রুল ফায়ারিং টেস্ট কীভাবে সম্পন্ন করবে?
18. নেগেটিভ টেস্ট অটোমেশন: সাধারণ বৈধ লগের একটি টেস্ট ডেটাসেট দিয়ে সিআই পাইপলাইনে কীভাবে ভ্যালিডেট করবে যে নতুন কোনো রুল কোনো অপ্রত্যাশিত ফলস পজিটিভ তৈরি করছে না?
19. রিগ্রেশন টেস্ট স্যুট (Regression Test Suite): একটি ডিকোডারের কোড পরিবর্তন করলে পূর্বের সব রুল টেস্ট পাস করছে কিনা তা নিশ্চিত করতে কয়েক হাজার টেস্ট কেস কীভাবে ২-৩ মিনিটের মধ্যে প্যারালালি এক্সিকিউট করবে?
20. টেস্ট কভারেজ মেট্রিক্স (Test Coverage): মোট রুলের কত শতাংশ রুলের জন্য সক্রিয় টেস্ট কেস বিদ্যমান রয়েছে, তা পরিমাপ করার অটোমেশন ড্যাশবোর্ড কীভাবে তৈরি করবে?

### Topic 05: Continuous Delivery & Deployment to Staging/Production

21. টেস্ট সফল হওয়ার পর সিআই/সিডি পাইপলাইন কীভাবে স্বয়ংক্রিয়ভাবে রুল ও ডিকোডার ফাইলগুলোকে স্টেজ এবং পরবর্তীতে প্রোডাকশন সার্ভারে শিপ করে?
22. Ansible Playbook, Terraform বা SIEM REST API ব্যবহার করে কোনো ম্যানুয়াল SSH বা ফাইল কপি ছাড়াই পুশ-বেসড ডিপ্লয়মেন্ট কীভাবে কনফিগার করবে?
23. ক্যানারি ডেপ্লয়মেন্ট (Canary Rule Deployment in CI/CD): পাইপলাইন কীভাবে নতুন রুলটিকে প্রথমে টেস্ট ক্লাস্টারে এবং পরবর্তীতে ৫% প্রোডাকশন নোডে সাইলেন্ট মোডে পুশ করে?
24. প্রোডাকশনে মাল্টিপল ডিস্ট্রিবিউটেড ম্যানেজারের ক্ষেত্রে সমস্ত নোডে কনফিগারেশন সিঙ্ক (Atomic Sync across cluster nodes) কীভাবে নিশ্চিত করবে?
25. ম্যানুয়াল অ্যাপ্রুভাল গেট (Manual Approval Gate): স্টেজিংয়ে সফল টেস্টের পর প্রোডাকশনে যাওয়ার আগে এসওসি লিডের "Approve" বাটনে ক্লিক বাধ্যতামূলক করার পাইপলাইন কনফিগারেশন কী?

### Topic 06: Zero-Downtime Rule Reload & API Synchronization

26. নতুন রুল বা ডিকোডার ডেপ্লয় করার সময় সম্পূর্ণ SIEM সার্ভিস রিস্টার্ট না করে গ্রেসফুল রিলোড (Zero-Downtime Hot Reload) কীভাবে এক্সিকিউট করবে?
27. সার্ভিস রিস্টার্ট দিলে যদি কয়েক সেকেন্ডের জন্য ইনকামিং লগ বাফারিং বা ড্রপ হওয়ার ঝুঁকি থাকে, তবে লাইভ API রিলোড মেকানিজম কীভাবে সেই ঝুঁকি দূর করে?
28. রিলোড করার পূর্বে কনফিগারেশন টেস্ট কমান্ড (যেমন: `wazuh-analysisd -t` বা `nginx -t`-এর মতো প্রি-ফ্লাইট সিনট্যাক্স ভেরিফিকেশন) চালিয়ে কীভাবে নিশ্চিত করবে যে কনফিগারেশন শতভাগ ত্রুটিমুক্ত?
29. যদি কোনো নোডে রিলোড ফেইল করে, তবে ক্লাস্টারের অন্যান্য নোডগুলোকে ডিসিঙ্ক (Desynchronized State) হওয়া থেকে রক্ষা করার উপায় কী?
30. রুল রিলোডের পর ক্লাস্টারের মেমোরি ব্যবহার এবং সিপিইউ স্পাইক ট্র্যাকিং কীভাবে করবে?

### Topic 07: Automated Rollback & Fault Recovery

31. প্রোডাকশনে রুল রিলোডের পর যদি কোনো নোড আনএক্সপেক্টেডলি ক্র্যাশ করে বা মেমোরি ১০০% হয়ে যায়, তবে পাইপলাইন কীভাবে স্বয়ংক্রিয় রোলব্যাক (Automated Immediate Rollback) ট্রিগার করবে?
32. Git-এর পূর্ববর্তী স্টেবল কমিটে রিভার্ট (`git revert`) করে কীভাবে ১ মিনিটের মধ্যে পুরো প্রোডাকশন এনভায়রনমেন্টকে লাস্ট-নোন-গুড (Last Known Good State) অবস্থায় ফিরিয়ে আনবে?
33. রোলব্যাকের পর পোস্ট-মর্টেম ও রুট কজ অ্যানালাইসিস (RCA) করার জন্য ফেইলিওর লগ ও কনফিগারেশন স্টেট কীভাবে স্বয়ংক্রিয়ভাবে সংরক্ষণ করবে?
34. আংশিক ফেইলিওর (Partial Failure: ৩টি ম্যানেজারের মধ্যে ১টিতে রুল পুশ হয়েছে বাকি ২টিতে নেটওয়ার্ক ড্রপ হয়েছে)—এই জটিল স্টেট কীভাবে হ্যান্ডেল করবে?
35. রোলব্যাক সাকসেসফুল হলে এবং সিস্টেম পুনরায় সুস্থ হলে এসওসি এবং ইঞ্জিনিয়ারিং টিমের কাছে স্বয়ংক্রিয় অ্যালার্ট নোটিফিকেশন পাঠানোর মেকানিজম কী?

### Topic 08: Out-of-Band Change Prevention & Single Source of Truth

36. এসওসি এনালিস্ট বা কোনো অ্যাডমিন যদি সরাসরি SIEM-এর ওয়েব কনসোলে গিয়ে বা সার্ভারে SSH করে কোনো রুল মডিফাই করে দেয় (Out-of-Band / Manual Drift), তবে Git-এর সাথে যে কনফ্লিক্ট তৈরি হয় তা কীভাবে বন্ধ করবে?
37. সার্ভারের রুল ডিরেক্টরিগুলোকে রিড-অনলি (`chattr +i` বা ফাইল পারমিশন লক) করে শুধুমাত্র CI/CD সার্ভিস একাউন্টের জন্য রাইট এক্সেস সীমাবদ্ধ করার নিয়ম কী?
38. কনফিগারেশন ড্রিফ্ট ডিটেকশন (Configuration Drift Detection): প্রতিদিন প্রতি ঘণ্টায় প্রোডাকশন রুলসেটের সাথে Git রিপোজিটরির হ্যাশ মিলিয়ে কোনো অননুমোদিত পরিবর্তন হলে তা অ্যালার্ট করার ক্রন স্ক্রিপ্ট কীভাবে লিখবে?
39. "Git is the Single Source of Truth": প্রোডাকশনে কোনো ম্যানুয়াল পরিবর্তন শনাক্ত হলে স্বয়ংক্রিয়ভাবে Git স্টেট দিয়ে প্রোডাকশন ওভাররাইট (Auto-Healing) করার কৌশল কী?
40. ওয়েব UI-তে রুল এডিটিং অপশনটি সম্পূর্ণ ডিজেবল বা হিডেন করে দেওয়ার কনফিগারেশন কী?

### Topic 09: Secrets Management & CI/CD Security Hardening
